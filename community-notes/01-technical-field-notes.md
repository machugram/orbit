# Orbit field notes

Recovered from the Orbit MCP server (`github.com/machugram/orbit`) on macOS + OrbStack. Each note is a place where the first reasonable implementation is wrong in a way the API does not report.

## Finding 1 — `orbctl create --cloud-init` is a no-op outside Debian and Ubuntu

### What happened
OrbStack only ships cloud-init in its Debian and Ubuntu images. On Alpine, Fedora, Arch, and Void, `orbctl create --cloud-init <user-data>` returns success and the VM boots with no `sshd` and no agent user. There is no error.

The working channel is `orb -m <vm> -u root sh -s`, which has root on every distro and both isolation modes. One POSIX script (`provisionScript` in `internal/vm/distro.go`) detects `apt-get`, `dnf`, `yum`, `zypper`, `pacman`, `apk`, or `xbps-install`, then `systemctl`, `rc-update`, or `sv`.

`Provisioner` retries that script 5 times, 3 seconds apart, inside a 3-minute timeout (`provisionRetries`, `provisionDelay`, `provisionTimeout`). Success is the stdout marker `ORBIT_PROVISIONED`. The username and the authorized-key line are `$1` and `$2`, passed as real argv to `sh -s`, so a key cannot break out of the script body.

### Why naive code fails
The spec assumed cloud-init runs once at first boot on every image. On the images that lack the agent, OrbStack accepts the flag and drops the user-data. The VM looks healthy in `orbctl info` and SSH never comes up.

### The fix (`internal/vm/provisioner.go`, `internal/vm/distro.go`)
- Provision after create, over `orb -u root`, and retry until `ORBIT_PROVISIONED` or the 3-minute budget ends.
- Keep a warm `orbit-base-<distro>` (`vm.BaseName`, `vm.IsBaseName`) so the package install happens once. Later machines are `orbctl clone` plus an `authorized_keys` inject. `Manager.Destroy` refuses names with the `orbit-base-` prefix.

## Finding 2 — A valid key is refused while the shadow field is `!`

### What happened
`orbctl` creates the `agent` user password-locked. `/etc/shadow` contains `agent:!:…`. OpenSSH treats `!` as a locked account and rejects public-key auth even when `~/.ssh/authorized_keys` is correct and mode `0600`.

### Why naive code fails
Installing the key and starting `sshd` is the whole checklist in every SSH tutorial. The lock lives in the password field, which pubkey auth is not supposed to consult. OpenSSH does consult it.

### The fix (`internal/vm/distro.go`)
- After writing `authorized_keys`, rewrite the lock to the disabled-but-not-locked marker:

```sh
sed -i "s/^$U:!*:/$U:*:/" /etc/shadow
```

- `*` keeps password login off. Pubkey auth starts working. The same script is idempotent, so the 5 retries do not fight each other.

## Finding 3 — The OrbStack SSH multiplexer ignores `authorized_keys`

### What happened
OrbStack's convenience SSH endpoint is `127.0.0.1:32222`. `orb ssh` uses it. It authenticates with OrbStack's own key, `~/.orbstack/ssh/id_ed25519`, and never reads `authorized_keys` inside the VM.

A key that is correctly installed still fails:

```text
ssh -p 32222 agent@<machine>@127.0.0.1
unable to authenticate, attempted methods [publickey]
```

### Why naive code fails
The multiplexer looks like a transport that saves you from learning each VM's address. Authentication happens before the proxy, and there is no setting that makes it honor the in-VM key. One host key would also collapse every VM onto a single credential.

### The fix (`internal/exec/runner.go`, `internal/exec/pool.go`)
- Dial `<vm>.orb.local:22` as user `agent` with that VM's Ed25519 key from the vault (`Resolve` returns `vmID + ".orb.local:22"`).
- Host-key check is `ssh.InsecureIgnoreHostKey()` on purpose: the host key is generated by `ssh-keygen -A` at first boot, and `.orb.local` resolves to a loopback address. Documented in ADR-011. Pinning is still required before any target is reachable off the machine.

## Finding 4 — `docker run -e NAME=value` publishes the secret; bare `-e NAME` does not

### What happened
`docker run -e POSTGRES_PASSWORD=s3cret` puts `s3cret` in the `docker` process argv, so it shows up in `ps` and `/proc/<pid>/cmdline`, and it has already passed through the model transcript to get there.

Docker treats `-e NAME` with no `=` as "copy `NAME` from my environment." Checked directly:

```sh
DEMO_SECRET=x docker run --rm -e DEMO_SECRET alpine sh -c 'echo $DEMO_SECRET'
```

prints `x`. `x` is not on the command line.

SSH has the same trap in the other direction. `TOKEN=value command` shows up in the remote process list. The runner sends the command as `sh -s` and writes this on stdin (`envWrapper` in `internal/exec/runner.go`):

```sh
export TOKEN='…'
exec sh -c 'requested command'
```

`shellQuote` wraps the value in single quotes and turns embedded `'` into `'\''`.

A second, related unwrap: `dockerCLI` reports failure as `fmt.Errorf("container: docker %s: %w: %s", args, err, stderr)`. Because the wrap is `%w`, `errors.As(err, &ee)` still finds `*os/exec.ExitError`. `commandResult` turns that into `Result.ExitCode` and a normal tool result. A non-zero command is data. Failure to start `docker` at all stays an error. A `%v` wrap would hide the exit code and surface every `false` as a tool failure, with stdout dropped.

### Why naive code fails
`-e NAME=value` is the example in the Docker docs. It is also the form an agent produces if you let it pass the secret as a tool argument. The value then lives in three places you did not mean: the transcript, the audit log, and the host process table.

### The fix (`internal/container/manager.go`)
- `secret_env` is `env var name → vault key name`. `resolveSecrets` reads the vault into the subprocess env map. `bareEnvFlags` appends `-e` and the name only.
- Literal env takes the same path, so ordinary values stay out of argv too. Secrets overwrite literals on a name clash.
- Audit logs the names (`envNames`), never the values. `secret_put` returns `{key, status:"stored"}` and does not echo the value. There is no read-secret tool.
- Empty file writes cannot use `cat > "$1"`: `dockerCLI` sets `cmd.Stdin` only when `len(inv.Stdin) > 0`, so a zero-byte payload never attaches a stdin. `PutBytes` uses `mkdir -p -- "$(dirname "$1")" && : > "$1"` in that case, with the path as `$1` rather than interpolated into the script.

## Finding 5 — `docker compose exec -f -` deadlocks on stdin

### What happened
Inline compose YAML is piped with `docker compose -f -` so Orbit never writes a temp file. That consumes stdin. `docker compose exec` also wants stdin for the command inside the container. Docker reads the YAML first, then blocks waiting for command stdin. Closing stdin early is version-dependent.

`docker compose -f -` also has no project directory. A relative `build:` context is resolved against the orbit process cwd, which is typically the user's home directory.

### Why naive code fails
`-f -` is the documented way to inject a compose file in CI, and `compose exec` is the documented way to run a command in a service. Together they share one file descriptor. A temp file removes the deadlock and adds a crash-leak and a concurrent-call race, which is why the provisioner already refused temp files.

### The fix (`internal/container/manager.go`, ADR-006, ADR-008)
- `ComposeUp` / `ComposeBuild` still use `-f -` and `Invocation.Stdin`.
- `ComposeExec` calls `ComposePs`, matches the `Service` field (the key under `services:`), and runs `docker exec` on the container name Compose generated (`myproject-api-1` for service `api`). Scaled services: first container whose state is running, which is what `docker compose exec` does by default.
- `service_down` for a compose project is `docker compose -p <project> down` with no file (`ComposeDownProject`). The project name is the identity; the YAML is not required to tear the stack down.
- Inline stacks that build should use an absolute context or a pre-built `image:`.

## Finding 6 — A destroyed VM is invisible to lookup and illegal to insert

### What happened
`vms.id` is `TEXT PRIMARY KEY`. `SetVMState(id, VMDestroyed)` runs `UPDATE vms SET state = ?, destroyed_at = ?`. It does not `DELETE`. `GetVM` still returns the row.

`findMachine` treats `state == destroyed` as absent, so `workspace_open` of the same name falls through to `Provisioner.Create` → `CreateVM` → `INSERT`. SQLite rejects the insert. The same tombstone is written when `Clone` fails (`SetVMState(name, VMDestroyed)` after the insert already committed). Closing a workspace and opening that name again fails even though `orbit://workspaces` no longer lists it.

A second lookup bug showed up while wiring that path. The first `findWorkspace` always called `docker ps -a`. Docker down meant opening a VM failed before OrbStack was consulted. `docker ps` also prefixes names with `/`, so a container named `box` arrives as `/box`.

Cleanup has the same shape on the context side. The command timeout cancels the parent `ctx`. `defer Destroy(ctx)` then does nothing, and the ephemeral VM survives. `destroyQuiet` uses `context.WithTimeout(context.Background(), 30*time.Second)`. A failed key inject uses `context.WithTimeout(context.WithoutCancel(ctx), 30*time.Second)` so the delete still runs.

### Why naive code fails
Soft-delete plus "not found means create" is the usual lifecycle. A primary key does not care that the row is logically dead. And a single lookup function that always asks every backend turns one down daemon into a total outage.

### The fix (`internal/tools/shared.go`, `internal/tools/run.go`, `internal/vm/provisioner.go`)
- `findMachine` reads the vault only: live VM, else live microVM. `findWorkspace` calls it first and lists containers only on a miss. A docker error is returned only in that miss path. Names are compared with `strings.TrimPrefix(c.Name, "/")`.
- `workspace_open` of `kind=vm` or `kind=microvm` uses `findMachine`, so a stopped Docker daemon cannot block a machine.
- Ephemeral teardown and failed-clone teardown each get a fresh 30-second context that the command timeout cannot cancel.
- `CreateVM` and `CreateMicroVM` still `INSERT` first. On a primary-key conflict they `UPDATE` the row only when `state` is `destroyed`, clearing `key_id`, `destroyed_at`, and the idle TTL. A live row is left alone, so a duplicate of a running name still fails.
