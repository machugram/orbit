# ADR-004: AES-256-GCM + Argon2id vault backed by SQLite

**Status:** Accepted  
**Date:** 2025-06

## Context

The server needs to persist three kinds of data:
1. Arbitrary secrets (API keys, tokens) — the `cred_*` tools
2. Ed25519 private keys — one per VM
3. VM metadata (distro, state, timestamps, key_id)

These live on the user's local machine. The design must protect secrets at
rest while remaining usable without a key management service.

## Decision

Store all data in a **single SQLite file** (`~/.orbit/vault.db`). Every
secret value is encrypted with **AES-256-GCM** under a fresh 12-byte IV
before being written. The AES key is derived from a user passphrase via
**Argon2id** (salt=32B, m=64MiB, t=3, p=4) and held only in memory.

A `vault_meta` table stores the Argon2id salt and an encrypted canary blob.
On `Open`, the canary is decrypted to verify the passphrase before any reads.

## Rationale

**Argon2id is the right KDF for a local vault.** It is memory-hard (resistant
to GPU/ASIC brute force), the winner of the Password Hashing Competition, and
directly recommended by NIST SP 800-63B. The parameters (64 MiB, 3 passes)
target ~300ms on a modern laptop — slow enough to resist brute force, fast
enough to not be noticed at server startup.

**AES-256-GCM provides both confidentiality and integrity.** The auth tag
detects any tampering with ciphertext; a corrupted or partially-overwritten
blob returns `ErrDecrypt` rather than silently producing garbage plaintext.
A fresh 12-byte IV per write ensures ciphertext uniqueness even for repeated
writes of the same plaintext.

**SQLite is the right persistence layer for a local secret store.** It is
a single file (easy to back up, easy to understand), handles concurrent
readers with WAL mode, requires no daemon, and is universally available.
The pure-Go `modernc.org/sqlite` driver produces a cgo-free binary (see
ADR-001). Write volume is low enough that the driver's performance overhead
is irrelevant.

**Public keys are not stored.** The public key (and hence the `authorized_keys`
line) is derived from the encrypted private key on demand. This is strictly
less material on disk than storing both halves, and eliminates any risk of
public/private key mismatch in the store.

**Canary-at-open for fast wrong-passphrase detection.** Without the canary,
a wrong passphrase would derive a different AES key, decrypt a credential to
garbage, and only fail when the plaintext failed application-level parsing.
The canary makes wrong-passphrase detection O(1) and produces a clear error
rather than a confusing decode failure.

## Consequences

- Changing the passphrase requires re-encrypting every credential row.
  `rekey` is currently unimplemented (ROADMAP §2.10).
- The derived key is never cached to disk; if the process restarts, the user
  must supply the passphrase again (via env var or Keychain).
- All writes serialize through a single SQLite connection
  (`SetMaxOpenConns(1)`) with WAL mode; reads can overlap writes but also
  serialize in the current configuration (ROADMAP §1.5).
- `modernc.org/sqlite` is slower than `mattn/go-sqlite3` under high write
  load but the tradeoff is acceptable at this write volume (see ROADMAP §1.7).
- Credential IDs are 128-bit `crypto/rand` hex strings generated by `newID()`
  in `store.go` — the same idea as `vm.randHex`. This dropped the
  `github.com/google/uuid` direct dependency (UUIDv4 is itself just 122 random
  bits) in favor of the stdlib, keeping the dependency surface minimal.
